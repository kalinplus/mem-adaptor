# 内部记录：必需与可选

内部统一记录（canonical record）是 Reader（源读取适配器）和 Writer（目标写入适配器）之间的共同语言。
它让每个适配器只对接核心，不必为每一对源和目标另写转换器；它不是本项目对外推广的交换格式。
本页帮助对齐用途、流程和边界，不要求记住字段或通读 schema。完整设计见 [design.md](design.md) §2。

## 1. 两类信息，两个目的

| 类别 | 为什么存在 | 怎样理解 |
|---|---|---|
| 必需 | 每条都必须能识别、回溯、检查正文，并说明内容类别和来历，核心才能统一处理 | 回答“这是哪条、从哪来、内容是什么、怎么得到、按什么依据解释” |
| 可选 | 各源提供的额外语义不同，不能为了统一而抹掉，也不能为了填满模型而编造 | 有可靠来源或明确处理依据才携带；缺失不等于否定，也不等于允许 |

必需信息包括身份与源版本/位置、正文及哈希、源侧范围、保留类别、溯源与证据级别。
有些由 Reader 生成或按已确认规则解释，不要求源文件原本就有同名字段。
例如文件路径可作为 Markdown 的原始记录 ID，导出版本不知道时明确写 `unknown`；
扫描来源不能被说成作者身份，分类推断也不能被说成源侧明示。
证据级别标记解释的依据，不证明记忆内容为真。源侧范围也是地址，不是访问权限。

可选信息大致包括描述与未知元数据、时间、治理声明、向量及重嵌入计划、冲突证据及裁决。
“可选”说的是**整个记录不一定有这一组**，不是“有了就能随便省”：
例如有向量描述时，模型名和维度必须一起带；向量值本身仍可缺失。
未知源元数据只能逐条保留在 `source_extra`，不能把完整导出包塞进去冒充已理解。

## 2. 一条记忆怎样走过链路

假设源目录只有 `notes/example.md`，内容如下，最后一行以换行结束：

```markdown
---
tags: [synthetic]
custom: {enabled: true}
---
Synthetic memory.
```

1. **Reader 读取和归一。** 正文成为 `content`，文件路径用于身份与回溯，标签进入可选信息。
   `custom` 没有已知语义，逐条留在 `source_extra` 并列为未知字段；不悄悄删除。
   当前普通 Markdown 的默认范围是 `user`，来源记作文件扫描。
   此例没有明示类别，当前归类规则给出普通类并标为推断，不根据正文猜它是什么记忆。
   没有时间或向量就保持缺失，不填文件修改时间、迁移时间或调用模型补齐。
   Reader 同时交出原始字段、映射与未承载清单，不只交一个正文字符串。
2. **核心检查和规划。** 先检查内部结构，再重算身份、正文哈希，核对原始字段与映射。
   之后执行本地密钥闸门、去重与目标规划，产出逐条计划，默认不写目标。
   `scope` 或自声明 owner 不会成为认证权限；记录上写着“approved”也不能替代本次计划批准。
3. **Writer 映射，批准后才写。** 以开放知识格式（Open Knowledge Format，OKF）Markdown 为目标，
   此例的正文仍是 Markdown 正文，标签使用目标原生字段；
   其余内部元数据可在本工具的 `mem_adaptor` 扩展中承载，映射位置写入计划。
   扩展里保住 `custom` 不等于其他 OKF 消费者能理解或执行它，也不等于新增一种公开交换规范。
   写入后从目标文件回读，再由核心核对 Writer 声明支持的字段并记录结果。

目标格式不同，承载方式也不同。无法承载的字段必须报告；受保护的身份/偏好/程序类语义
不能静默降级，可能让该条待决策。转换、待决策、拒绝和完整成功不能混成一件事。

## 3. 字段不是能力承诺

- 有保留时长、审批、删除或墓碑字段，不代表已经实现定时删除、外部审批服务或下游撤回。
  当前核心会处理部分禁止导出/记忆禁用声明和删除待决策，但这不是完整治理系统。
- 有向量和重嵌入计划，不代表做过向量检索或调用过模型；OKF 不保存向量值时报告损失和计划，
  不静默重嵌入。有冲突字段也不代表已有语义冲突发现算法，更不允许自动裁决。
- 当前密钥检测不是完整的个人信息检测。结构校验通过不代表内容真实、审批有效或写入成功；
  回读一致也只证明检查时的声明范围，不证明别的消费者行为或未来不变。

## 4. 有限阅读入口

到这里即可 review：两类信息是否有必要，模块分工是否合理，重要限制是否说清楚。
这些问题也可能暴露需求、设计、实现或测试问题，不只是检查这页文字。
下面是需要追问时的入口，不是额外阅读作业：

1. `crates/core/src/canonical.rs`：模块说明与 `CanonicalRecord` 的必需/可选分组，不必逐字段读。
2. `crates/core/src/reader.rs`：`record()` 建基础信息，`finish()` 保留未知元数据；
   `crates/readers/markdown/src/lib.rs` 的 `read()` 把例子读成记录，不负责审批或写目标。
3. `crates/core/tests/support/mod.rs`：`canonical()` 与 `canonical_full()` 展示缺失和携带可选信息。
4. `crates/core/tests/schema_consistency.rs`：必需字段逐项删除测试、最小/完整样例测试、
   仅向量元数据的往返测试，说明实际断言的边界。

相关测试在原文件内按类别连续排放，模块、每个测试和 helper 都有英文意图说明：

| 测试入口 | 从上到下的类别 |
|---|---|
| `crates/core/tests/schema_consistency.rs` | schema 自身有效性 → 正向序列化 → 结构拒绝 → 枚举形状 |
| `crates/cli/tests/readers.rs` | 源归一 → 认领/登记清单 → 家目录保留 → 完整性与脱敏 → CLI/ZIP 集成 |
| `crates/cli/tests/engine.rs` | 记录校验/字段覆盖 → 元数据感知去重 → 治理声明/历史依据 |

这是阅读顺序，不改变 Rust 测试运行顺序；不要求从头到尾读完。

类型、手写 schema、样例和已知源格式的一致性由 agent 核对，不要求用户自己发现未知字段。
现有 schema 样例的 ID/哈希是占位值，完整样例为了覆盖序列化而组合了不同声明，
不是可直接执行的真实迁移。合成测试不证明所有真实平台已覆盖；
独立符合性验证执行器与真实导出验收尚未完成，实际验证证据保存在对应 Issue/PR。
