# OKF 迁移审查：哪些环节还不能放心

**结论：正常迁移能跑通，但现在还不应通过 OKF Writer 的完整验收。**
最要紧的两处问题是：批准后的目录可以被调包，写入却仍被记为成功；合法笔记中的分隔符可以让迁移写完后无法回读。

这里的 OKF（Open Knowledge Format，开放知识格式）是目标 Markdown 目录格式；
Writer 是把内部记忆写成这种格式的模块。本轮审的是现有实现，不是重新设计记忆库，也没有修产品代码。
审查基线为 `3cf5e92`，需求和逐项证据在 [Issue #6](https://github.com/kalinplus/mem-adaptor/issues/6)。

## 先看流程，问题出在哪

```text
源记忆
  → 读取、校验、筛选
  → 检查目标与历史，生成计划
  → 用户批准
  → 再检查执行依据，写出记忆、索引、日志
  → 回读，核对输出
  → 保存回执
```

用户需要的不是“最后退出码是零”，而是五件事：

| 环节 | 用户真正要的保证 | 这次发现的缺口 |
|---|---|---|
| 批准到写入之间 | 批准哪里，就只写哪里 | 检查了路径名，却没有守住路径背后的目录 |
| 写入前处理目标 | 坏记录拦住，用户文件不动，能迁的继续报告 | 身份损坏没拦住；普通同名文件却拖垮整份计划；特殊文件能让程序卡住 |
| 输出目标格式 | 不改原文，而且写出的目录真的符合目标约定 | 自己写出的合法文本可能自己读不回；部分作者、索引、日志格式也没对齐 |
| 写入后遇到失败 | 明确告诉用户写到了哪、哪些事还没完成 | 文件可能已改变，提示却只有一条底层错误 |
| 测试与回执 | “成功”有证据，证据的边界说清楚 | 部分测试只证明报错；内部字段相等被误当成整个迁移可靠 |

下面按这五件事解释，不按审查工具的发现编号罗列。

## 1. 批准不能只绑定一个路径名

**这一处不是格式小毛病，是写入边界失守。**

目前计划会记录目标路径、已有文件的哈希，写入前也会重新核对。这些检查能抓住普通文件被修改，
但没有检查目标目录的上层目录是否被换成了符号链接。

实际探针在最后写入入口，把原目标的父目录移走，再把原父路径链接到另一个隔离目录。
路径文字没有变，已有目标也仍然“看起来不存在”，所以检查通过了。
结果是：**三个产物写进了另一处目录，原批准目录没有目标，引擎却返回了验证成功的回执。**
这个复现有固定注入点，不靠碰运气制造竞争。

另一个现象要区别看：命令行会接受用户一开始就给出的目标根链接，并把计划路径改成链接指向的真实目录。
这违反当前“拒绝目标符号链接”的契约，但审批确实绑定了那个真实目录，**不是同一种批准后调包**。
不能把两者混成一个更吓人的结论。

修复重点是守住实际写入位置，而不是再加一次正文哈希比较。
没有跨进程锁是已声明的限制，但不能用它解释掉这个在写入入口就已经可见的路径变化。

## 2. 写入前的判断：该拦的没拦，该隔离的没隔离

这一段负责回答：“目标里已有的东西，到底是我们的记录、用户的文件，还是无法可靠读取的对象？”
判断错了，后面的写入与回执再认真也补不回来。

目前有三种不同后果，不能都叫“迁移失败”：

- **损坏身份混进受管目录。** 修改旧记忆的来源系统，却不改它的内部编号，两者已经不匹配。
  预检只看结构和文件名，没有核对身份关系。随后迁入另一条记忆仍然成功，损坏记录继续进入索引。
  新记录的成功回执不代表旧记录也被证明正确。
- **无关用户文件阻断整份计划。** 用户普通笔记恰好占了本次记忆的同名路径，文件没有被覆盖，这一点是安全的。
  但程序把它当成坏迁移信封，直接中止整个计划。按已有契约，应该把这一条列为“存在但没有可靠历史依据”，
  不接管它，并继续说明其他合格记录的处置。
- **特殊文件让程序一直等。** 目标索引如果是命名管道，而不是普通文件，读取会阻塞。
  本轮只在隔离目录里做了有超时的子进程探针，没有影响真实文件或其他进程。

这里要补的是目标分类和失败边界，不是放宽解析、猜测身份或自动修复用户目录。
也不涉及已经延期的卫星编号和家目录编辑策略。

## 3. 写出原文，不等于写对了目标格式

**最直接的问题是：合法内容也能把迁移卡死在写后验证。**

例如正文首行是 `Heading---`，或者未知 metadata 的多行字符串里有一行缩进的 `---`。
源文件合法，写出的 YAML 也合法。但回读代码不是识别独占一行的结束符，而是在任何位置寻找 `---` 加换行。
它把字段内容当成了信封结束。

实际结果不是“这条没写”：记忆、索引、日志已经写完，回读才报错，最终回执没有保存。
这同时说明，未知字段“有保留通道”还不够，保留下来的合法值必须能被可靠读回。

另一类问题没有让命令报错，却没有对齐 OKF 的原生约定：

- 作者信息没有完整映射：有更新时间、没有可用作者时仍输出不完整的生成信息；
  人类作者没有转换成约定的 `human:` 标记。
- 根索引和日志的结构没有对齐规范：根索引带额外的管理字段；日志没有按日期分组，也不是最新在前。
  当前 Reader 识别和 Writer 所有权判断依赖那些索引标记，不能只删字段就说修好了，必须协调两端。
- 映射报告有“空报”：源记录没有更新时间，目标也没有生成时间，报告仍声明了这条时间映射。
  这是此前已发现的问题，不算本轮新发现。

这些后果有轻重之分。分隔符错误直接破坏迁移完成；作者信息可能误导消费端；
索引、日志属于格式契约偏差。OKF 对可选信息有宽容规则，不能因此宣称所有消费者都会拒读，
但也不能用“自家回读通过”证明格式已经完全正确。

## 4. 写到一半失败，必须说清楚已经发生什么

当前按文件逐个替换，没有整批事务。**这本身是明确接受过的能力限制，不是这次才发现的缺陷。**

问题是失败提示没有把这个限制讲给正在操作的用户：

```text
记忆文件写入成功
  → 索引写入失败
  → 命令退出，没有最终回执
```

本轮在隔离目录里分别制造了“第一份记忆写出之前失败”和“记忆写出之后、索引写出之前失败”。
前一次目标文件完全没变，后一次已有新记忆；两次都有审批文件，都没有最终回执。
但最后的错误都只说权限不足，没有说明目标可能部分改变，也没有告诉用户先检查目标和凭据，不能盲目重试。
回读失败也有同样的问题。

最后一步“回执保存失败”的提示已经做对了：说明目标可能已变、审批已保存、可靠回执未保存，并要求先检查。
**需要把这种诚实延伸到前面的写入、回读和验证边界。**
不是承诺回滚，更不是自动重试。

## 5. 测试和 verified，到底能证明什么

**134 项测试通过，不等于上面这些问题不存在。它只说明现有断言都满足了。**

部分失败测试只问“有没有报错”，或者只比较一份记忆文件。
如果程序先覆盖索引，再报另一个错误，这种测试仍可能通过。
还有快照把不完整作者信息和不符合规范的索引、日志固定成了预期，比较得再精确也只能证明“仍然输出同一种错误”。

回执里的 `verified` 也有边界：引擎核对的是 Writer 声明支持的内部字段，以及这次输出的字节证明。
它不是“目标格式全部合规”“实际目录没有被替换”，更不是“记忆事实经过人工核实”。

这轮有实证的部分也要保留：

- 正常合成笔记的正文和未知 typed metadata 能完整保留，实际记忆、索引和日志与既有快照一致。
- 向量被明确移除，模型、维度和归一化声明保留；重建计划显式报告，已有计划没有被覆盖。
  第二轮不重复写入，也没有调用模型。
- 目标内部的记忆目录、记忆文件、索引和日志链接能被拒绝，无关用户日志保持不动。
- 用真实引擎签发的写入凭证去改正文、增加条目或换目标，会被拒绝，目标没有写入。
  但这些反例尚未成为仓库里的回归测试。

变异测试是另一种检查：故意改坏代码，看测试能否发现。
本轮 37 个变异中，24 个被捕获、3 个存活、10 个无法编译，没有超时。
三个存活项都有实际区分见证，都是缺场景：目录读取错误、只坏一个文件名条件，以及读取错误被误当成记录不存在。
**这是测试债，不是原实现已经发生了这三种错误。**

## 建议先修什么

不要按发现数量平铺派任务，按风险拆成可验收的小批次：

1. **先堵住会写错位置、写完却无法完成的入口。** 修目标祖先变化与分隔符识别，
   同时给这些失败补真实副作用与凭据断言，明确告诉用户是否可能已经写入。
2. **再修写入前的目标判断。** 区分损坏受管记录、无历史用户文件和特殊文件。
   验收重点是“不接管、不假装不存在、不拖垮可处理记录、不挂住”。
3. **最后统一原生格式与报告口径。** 协调作者、索引、日志与字段映射，
   用独立的格式依据重审快照，不让 Writer 和 Reader 互相自证。

测试缺口随对应批次一起补，不另做“全部测试绿了”的大扫除。
这里是修复优先级建议，**不是修复授权**。不自动开始 UMP（Universal Memory Protocol，通用记忆协议）Writer 审查，
也不恢复 M6。

## 给人工 review 的两个抽查点

不必从头读几十个文件，先回答两个问题：

1. 读 `crates/cli/tests/writers.rs` 的 `writer_output_proofs_reject_changes_before_write_after_write_and_after_read_back`：
   它检查的是共享文件字节变化，还是也能发现目录被换掉？本轮路径探针说明后者不能借前者证明。
2. 读 `crates/cli/tests/m3_failures.rs` 的 `final_receipt_failure_reports_already_changed_target_without_success`：
   它如何同时检查目标、审批、回执和提示？前面的写入故障测试应该达到同一类证据强度。

## 附录：实现者的定位入口与证据边界

| 业务位置 | 先读实现 | 对照测试 |
|---|---|---|
| 批准后实际写到哪里 | `crates/core/src/writer.rs` 的 `read_file`、`atomic_file`；`crates/core/src/engine.rs` 的 `apply` | `writers.rs` 的竞争与输出证明测试 |
| 目标分类与受管预检 | `crates/writer-okf/src/lib.rs` 的 `managed_records`、`inspect`；引擎历史对账 | `review_regressions.rs` 的受管/无关记录测试 |
| 原生格式与回读 | OKF `write`、`inspect`、`plan`；`docs/m5-writer-proposal.md` | `writers.rs` 的原生字段、向量和快照测试 |
| 失败、审批与回执保存 | `crates/cli/src/main.rs` 的 `run`；引擎 `apply` | `m3_failures.rs` 的最终回执故障测试 |

**有证据：**两遍独立全文审查均覆盖指定 20/20 文件；主会话复现并检查实际产物、目标副作用和凭据。
原始 17 条发现经判定合并为 13 个新问题主题，另有 1 个历史已知映射问题；逐项判定、场景矩阵和变异见证交付到 Issue，
正文不拿这些编号要求人逐条消化。

**只是承诺：**文档规定所有相关失败都应说明阶段、目标状态和下一步；目前只有部分边界得到完整验证，不能宣称全部实现。

**未覆盖：**真实导出、独立符合性验证、断电、真实磁盘满、跨进程锁，以及全部跨文件/跨目标中断位置。
没有整批事务或安全重试承诺；已确认的家目录编辑和卫星身份细节仍按原约定延期。

实际验证：`cargo test --workspace --offline`、`cargo fmt --all -- --check`、
`cargo clippy --workspace --all-targets --offline -- -D warnings` 和 `git diff --check` 通过。
变异实验退出码为 2，表示存在存活项，不是普通测试失败或环境故障。
原生格式依据为已核实的 OKF v0.2 SPEC，参考提交 `ad30107c31c06aec8a7d5636e0d1058118604e6f`；
它不作为产品或测试的运行依赖。本轮所有运行探针都使用合成数据。
