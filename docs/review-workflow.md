# 协作规则：代码意图说明与 Issue/PR 人工 review

记录日期：2026-10-06。来自用户对 M0–M5 集中交付的反馈。
规则已写入项目 [AGENTS.md](../AGENTS.md)，采用 `/issue-workflow` 管理正式任务。
本文约束说明、交付和人工放行；创建 Issue、提交或发布须获得相应用户授权。
不因规则落地而自动批量补代码注释、修改全局指令或恢复 M6。

## 1. 问题与目标

前五个阶段的结果一起交给用户，阅读量已经超过一次有效 review 能承担的范围。
文件和函数缺少就地的意图说明，用户必须先读懂大量实现，才能反推它应该做什么，
再判断实现是否符合设计。即使测试通过，这个负担也没有减少。

目标不是让用户读完 AI 生成的全部代码，而是让用户能在较短时间内回答：

1. 这次承诺的功能是什么，哪些事情明确不做？
2. 哪些文件和函数承担这个功能，为什么这样分工？
3. 注释写出的意图、实际代码和验收测试是否一致？
4. 当前这一步是否可以通过，是否允许进入下一步？

根因是两个独立问题：代码没有充分说明意图，交付没有控制人工 review 的批次大小。
只加注释不能解决累计交付量，只拆批次也不能代替代码说明。

## 2. 代码说明规则

### 文件顶部

每个手写源文件都要有顶部说明，包括测试文件和辅助脚本。
简短说明它的职责、在调用链中的位置；有重要边界时说明它不负责什么。
说明写在文件内，不能只把读者引向仓库外的一份长文档。

Rust 用模块文档 `//!`，Python 用模块 docstring；代码注释保持英文。
JSON 不添加非法注释，schema 用适当的 `description`，数据 fixture 在配套 README 解释。
第三方原样复制和自动生成文件不直接改写，以配套说明标注来源与用途。

### 函数与方法

每个手写函数和方法都要有简短说明，包含私有 helper、trait 方法和测试函数。
trait 实现若没有额外行为，可以用一句话指向契约；有特殊行为必须单独说明。

- 简单函数：一行说明目的即可，Rust 可用 `///` 或普通 `//`。
- 复杂函数：用完整一些的文档，说明目的、输入输出的含义、
  关键约束、主要失败条件和副作用。只写适用于该函数的内容，不套空模板。
- 测试函数：说明它验证什么行为或回归，不只重复测试名。
- 非直观的分支：必要时补充“为什么”，不逐行翻译代码。

例如：

```rust
//! Derives stable record identities; it does not perform content deduplication.

/// Derives a stable ID from the source system and its native record ID.
fn canonical_id(system: &str, native_id: &str) -> String {
    // Implementation omitted in this documentation example.
    todo!()
}
```

说明必须来自实际阅读与设计，不根据函数名猜测行为。
代码改动时同步更新说明；发现说明与实现不一致，明确报告并修正，不用注释掩盖缺陷。
注释用于表达可核对的意图，不把“安全”“幂等”“已验证”等未经限定的承诺写进去。

## 3. 交付与停止规则

**实现方案获批、测试通过、人工 review 通过，是三个不同状态。**
前两者都不能视为用户已经验收实现。AI review 也不能替代用户放行。
正式任务以 Issue 承载已确认范围，以 PR 承载候选实现；合并前不是成功完成。

一次只推进一个可独立说明和验证的小功能。M0–M7 是规划里程碑，
不天然等于合适的 review 批次；大里程碑必须拆成更小的切片。
如果一轮必须跨多个模块，先解释不可拆的原因并让用户确认范围，
不要为了文件数少而制造错误的接口拆分。

每个切片按以下顺序进行：

1. **定范围**：说明本轮做什么、不做什么、预计修改位置和验收行为，形成 Issue 验收条件。
   非平凡设计仍先给实现路径、取舍和推荐，等待用户选择。未澄清的任务不派发。
2. **实现与验证**：只完成已确认范围，补齐文件/函数说明，
   在该任务的 worktree 运行相关测试，报告真实结果和剩余限制。
3. **交付 review 包**：给出简短行为总结、改动文件与关键函数的阅读顺序、
   对应的测试或合成输入输出，以及需要用户判断的问题。
   只列本轮重点，不再次倾倒整个仓库和此前阶段。草稿 PR 就绪后将 Issue 标为 `status:review`。
4. **停下**：完成本轮交接后，明确“候选实现已交付，等待人工 review”，结束当前回复。
   不领取、探索或实现下一任务，不启动下一任务的子 agent 或后台任务，
   不把沉默、旧方案批准或“测试通过”当成放行。
5. **讨论与修正**：用户提出的问题在本轮内解决并重新验证；
   若需要扩大范围或改变设计，重新确认。不对已授权范围内的每个小修复反复请示。
   修正后再次交付等待 review，不把修正授权当成下一任务授权。
6. **显式放行**：用户验收并确认合并当前 PR，成功合入后关闭关联 Issue。
   只有用户另外明确指派下一个任务，才进入下一轮；可以在同一条消息中给出两项授权。

建议交付摘要：

```text
本轮目标 / 非目标：
关联 Issue / 草稿 PR：
阅读顺序：文件 → 关键函数 → 对应测试
验证：实际运行的检查、结果、未覆盖项
需要确认：当前实现是否符合预期
状态：status:review，等待人工 review，未开始下一任务
```

这里的停止点是协作上的 review 门槛，不是迁移工具里的写盘审批，两者不要混淆。
review 包的具体结构见 §4。

## 4. 人工 review：人判断什么

人 review 的目的，是让自己对架构的理解清晰并与实现对齐，从中发现需求、设计、实现或测试上的问题；
没有发现问题，也可以确认对齐后通过。人不负责语法、风格、lint 和编译错误，这些交给工具和
[review-rules.md](review-rules.md) 定义的自动 review。

**agent 可以验证“实现是否符合契约”，不能替人决定“契约是否值得接受”。**
因此 review 的负担这样分配：

| agent 先交付 | 人判断 |
|---|---|
| 本轮意图、范围与非目标 | 意图是否符合需求 |
| 写成“必须 / 禁止”的契约，以及实现位置和关键取舍 | 分工、复杂度和取舍是否合理 |
| 每条结论的证据分类（见下） | 证据是否覆盖自己关心的情况 |
| 已知限制与未覆盖项 | 每项剩余风险是否可以接受 |
| 自动 review 与变异测试的结果，以及 agent 对每条发现的判定 | 判定是否可信，是否需要修改 |

### 证据三分类

review 包中的每条结论必须标为其中一类，不能混写：

- **有证据**：给出测试名和关键断言，或实际运行命令及输出。
- **只是承诺**：只有文档或注释说明，没有可执行的验证。
- **未覆盖**：明确没有处理或没有验证，并说明原因。

“测试通过”本身不是证据分类，必须说明该测试断言了什么。

### 高风险抽查

写入、历史保护、审批、密钥检测与报告保存路径，每轮挑 1–2 个相关测试由人亲自读。
只问一个问题：**“如果这项行为坏了，这个测试会失败吗？”** 回答不了，就是证据缺口。

### 每轮结论

一轮 review 只留下三种结论之一，并记录到 Issue：

- **通过**：意图、契约、证据与剩余风险都已接受。
- **需要修改**：指出具体的不匹配之处；修改仍在当前范围内。
- **待澄清**：还有问题需要回答，暂不判断。

不要求每轮都提出修改。理解的过程中可以追问“为什么这样做”“哪些事情不该做”
“遇到变化或失败该怎样处理”“哪个结论有证据、哪个只是承诺”。

### review 包结构

```text
意图 / 非目标：
契约（必须 / 禁止）：
阅读顺序：文件 → 关键函数 → 对应测试
结论与证据：每条标为 有证据 / 只是承诺 / 未覆盖
自动 review：工具、范围、覆盖率、发现及 agent 判定（真实 / 误报 / 重复）
变异测试（阶段 review）：存活变异及分类
已知限制：逐条，待人接受或要求修改
高风险抽查建议：1–2 个测试及要回答的问题
需要人判断的问题：
```

## 5. Issue/PR 是任务状态正本

一个正式任务对应一个 Issue、一个 worktree、一个分支和一个 PR。
不再使用 `PROGRESS.md`、新 specs 或 `REVIEW-STATUS.md` 维护任务状态；
会话 TODO 只是当前任务的临时工作清单，不构成另一本账。
现有里程碑方案和进展记录作为历史资料保留，不追加新任务状态。

| Issue 标签 | 含义 | 本项目的动作边界 |
|---|---|---|
| `status:inbox` | 想法未澄清 | 先澄清，不执行 |
| `status:ready` | 边界与验收条件已确认 | 用户明确指派后才能领取 |
| `status:running` | 已领取，有关联分支或 PR | 只执行指定任务的需求快照 |
| `status:blocked` | 等待决策、依赖或外部条件 | 交接后停止，不自行绕过 |
| `status:review` | 候选实现已交付 | 等用户验收，不开始下一任务 |

同一 Issue 同时只保留一个状态标签。成功完成以 PR 合入后 `Closes #N` 自动关闭为准。
用户决定放弃的尝试可以关闭，但要说明不采用原因，不能算作成功。

### Issue 和交接内容

正文使用六部分：目标 / 边界 / 验收条件 / 依赖与资料 / 当前交接 / 关联实现。
正文保存当前有效结论，评论保存变化和执行过程；达成新结论时更新正文。
执行开始记录采用的需求快照，新增大要求另开任务，不偷偷改变本次验收标准。

每次交接只记录紧凑证据：尝试编号、工具/模型、需求快照、起始提交、
产出提交/PR、验证与结果、阻碍、下一步。长日志引用测试产物，不内联到交接。
新会话或“继续”指令先同步指定 Issue 正文、评论和关联 PR，
只读直接依赖与相关文档，不遍历全部历史，不从整个 ready 队列自行挑任务。

### 派发与交付边界

- 首个 Issue 派发前，核对用户确认的项目目标、架构与模块划分；
  现有依据为 [design.md](design.md) 和 [implementation-plan.md](implementation-plan.md)。
- worktree 建在项目同级目录，派发前核对已提交基线、忽略文件和验证环境的自足性。
  初始基线提交须有用户授权，不自行把未审阅内容提交成基线。
  基线只是保存候选实现，不代表已通过人工 review。
- 共享可变文件只由主会话写。并行任务必须触达不同文件，同时不超过 3 个；
  并行只限用户明确授权的任务，不用并行突破人工 review 停止点。
- PR 交付前加载 `pr-delivery`，逐条核对 Issue 验收条件并给出证据；
  主会话自审 diff、复跑相关验证，只有有证据的条件才可标通过。
- AI review 意见由主会话筛选后交给执行 agent，不进行无人监督的互改循环。
  用户明确指派任务时，按 `/issue-workflow` 授权建立草稿 PR；启用 skill 本身不授权远端写入。
- 长期有效的接口和行为变化在同一 PR 更新文档；文档描述当前系统，
  Issue/PR 保存需求、原因与状态，不在任务关闭后另造进度账本。

不能伪造编号或在未核实前声称 GitHub 状态已更新。
存量任务迁移与正式任务派发遵循用户明确授权的范围。

## 6. 当前仓库的补救建议

M6 保持暂停。M0–M5 的工程验证结果保留，但不声称用户已经完成全部代码 review。
不要立即再交付一个“全仓库注释补齐”的大改动，否则只是把原来的阅读债换成注释阅读债。

推荐按功能补说明、补阅读入口并逐轮讨论，而不是要求用户重新从 M0 一直看完 M5：

1. 先选一个很小且独立的功能，例如记录身份生成，核对说明和对应测试，试运行新的 review 节奏。
2. 再依次选报告契约、计划与审批、历史保护、单个 Reader、单个 Writer；
   每个方向仍按复杂度拆分，不要求一次看完整个模块。
3. 每轮只补本轮涉及的文件顶部及函数说明，后续将验收范围与结果记录在对应 Issue/PR。
   逐步覆盖现有手写代码，不以批量生成注释代替真正核对。
4. 补说明时发现缺陷，单独指出并确认修复范围，不把行为修改混进“仅注释”交付。
5. 用户明确允许恢复后，再开始 M6 的第一个小切片，而不是一次做完整 M6。

这是建议的补救路线，本次没有执行上述代码改动。

## 7. 规则落点与保证边界

| 位置 | 适合放什么 | 局限 |
|---|---|---|
| 本文件 | 反馈原因、完整规则、示例和补救方案 | 由项目指令要求阅读，不代替状态 |
| 项目 `AGENTS.md` | 强制执行的说明要求、任务授权与停止规则 | 是 agent 行为约束，不是外部拦截器 |
| [review-rules.md](review-rules.md) | 自动 review 的路径规则、低价值测试写法与变异测试分类 | 自动 review 只能发现问题，不能证明没有问题 |
| GitHub Issue/PR | 需求、交接、验收证据、合并结果 | 标签本身不会阻止 agent 越界 |
| 用户全局指令 | 其他项目也适用的偏好 | 本轮未修改，推广需用户确认 |

现有“不要添加不必要注释”的偏好需要澄清为“不要冗余地复述代码”，
不能用它免除上述意图说明。为既有代码补说明本身也是一个有明确范围的任务。

**项目指令 + Issue/PR 可追踪交接 + 交付后结束回复 + 下一任务重新授权**，
是当前采用的协作约束，不提供技术上的绝对保证。
若需要硬性拦截，必须由 agent 之外的执行层检查授权；PR 审批/分支保护也只约束合并，
不能单独阻止 agent 开始下一任务。本项目尚未配置 hooks、外部授权门槛或仓库分支保护，
不声称已经具备这些能力。
